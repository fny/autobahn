Two synchronization tools were given the same trees on the same hardware and asked to do the same work: carry a stream of file edits from one machine to another while simulated coding agents churned the tree underneath them. The question was not who transfers a tree fastest — that turns out to be a storage question — but how quickly a single edit becomes visible on the far side, and what each tool costs to keep running while it waits.

Autobahn is faster in all fifteen cells, by between 1.5× and 37.8×, and uses three to eight times less memory. The gap widens with both tree size and concurrency, which is the more useful result: the two tools do not merely differ by a constant, they scale differently.

Propagation latency

The time from a file being written on one machine to exactly those bytes being readable on the other, confirmed by digest. Both timestamps come from one clock on the writing host, so no clock difference between machines can enter a sample, and each interval includes the confirming read and the reply's network trip. Every number is therefore an upper bound on the tool's own time. The harness measured its own overhead at 0.6 ms across all 150 jobs.

The pattern that runs through every row is that autobahn's latency is close to flat in both tree size and agent count, and mutagen's is not. On the 4k corpus mutagen goes from 62 ms at one agent to 2,680 ms at a hundred; autobahn goes from 101 ms to 84 ms. Mutagen's cost tracks how much work it must redo to notice a change, which grows with both the size of the tree and the rate of churn in it. Autobahn's tracks the change itself.

This also explains the one result that looks anomalous. On a small tree with a single writer, mutagen can watch every directory natively and detect a change almost immediately — hence 62 ms, genuinely faster than autobahn's 101 ms. That advantage does not survive scale in either dimension.

The two tools scale differently

The ratios matter less than their direction. Autobahn's median moves from 40 ms to 782 ms across the entire matrix — a factor of about twenty, spanning a 125× change in tree size and a 100× change in writer count. Mutagen's moves from 62 ms to 11,600 ms, a factor of 187.

The clearest demonstration holds the tree constant. On the 4,000-file corpus, as writers go from one to a hundred, mutagen goes from 62 ms to 2,690 ms. Autobahn goes from 41 ms to 78 ms. Nothing grew; only the churn did.

The cause is structural. No official mutagen build enables recursive watching on Linux, so a change event triggers a scan of the whole tree rather than of what changed. Its coalescing timers also reset on each event rather than expiring, so under continuous writing they postpone rather than batch. Autobahn scans only the paths its watcher marked, and caps its settle window regardless of how long writing continues.

On Chromium mutagen peaks near 2 GB on the source host where autobahn uses 249 MB. The ratio is 3.1× on a 4,000-file tree and 8.2× at 505,000 — a per-file cost rather than fixed overhead. The marginal cost of one additional file is roughly 4,022 bytes for mutagen against 507 for autobahn. Two gigabytes matters on a laptop or a small VM; 249 MB does not.

Two CPU results deserve separating out. Idle: with the tree synchronized and nothing happening, mutagen holds half a core on Chromium while autobahn uses two tenths of one percent. The destination host: in one-direction cells it does no editing, yet mutagen sustains more than a core there against roughly a third for autobahn — it rescans and reserializes the whole tree every cycle.

The practical reading is that first sync is not where these tools differ. The difference appears afterward, in how cheaply each one stays caught up.

Where autobahn is weakest

Autobahn leads every cell at the median, so its weaknesses are in the tail rather than in the ranking. Two are worth stating plainly.

  • Heavy bidirectional load. At chromium-100-bidir — 200 agents editing 505,000 files in both directions at once — autobahn keeps the better median (5,413 ms against 11,600 ms) but its 90th percentile is worse: 16,451 ms against 15,831 ms. Its tail discipline holds everywhere else and breaks here. This cell also produced most of the run's skipped ticks, so the offered edit rate fell slightly short for both tools.
  • Occasional multi-second outliers. In several cells autobahn's 99th percentile sits far above its 90th — on chromium-1, 16,188 ms against 286 ms. Per-run medians are tight across the ten machines (182.7–202.0 ms), so this is systematic rather than one bad run: roughly one edit in a hundred stalls for seconds.

The cause of the second is not established. The leading candidate on large trees is the 120-second periodic full scan, which exists to bound how long a missed filesystem event can persist and which takes seconds on a 505,000-file tree. That does not explain a 4,204 ms 99th percentile on the 4,000-file corpus, so a second mechanism is likely. This is open work, and it is the kind of defect only many repeats can surface — three would not have shown it.

What makes these numbers trustworthy

The measurement plane is a single compiled binary deployed to both hosts, so both sides run byte-identical instruments and the rules for what counts as a file exist in exactly one place. The design was reviewed adversarially across five rounds, and every finding was fixed before any number here was collected.

150 of 150 jobs completed. One run was excluded: a destination host became unreachable mid-job, the cleanliness check could not verify its state, and the run was recorded as failed rather than reported. That is the harness behaving correctly — an infrastructure failure produced a missing result, not a wrong one.

  • Convergence is content-verified. A sync completes when the destination's digests match the source's, never when a file count matches — and only a tree walk that recorded zero errors can certify it.
  • The working set is fixed across agent counts. The measuring agent edits the same 40 files whether 1 or 100 agents are running, so concurrency changes load and nothing else.
  • Per-run medians cluster within a few percent across ten different machine pairs, so the results reflect the tools rather than the hardware.
  • Both tools run on the same pair, in an order randomized per job, so machine identity and ordering effects cancel instead of confounding.
  • Timeouts are censored data, not discards. An edit exceeding its deadline holds its position in the percentiles. Across all 150 jobs and ~440,000 samples, zero were censored.
  • The harness measures its own overhead. The floor — arm, write, verify, acknowledge — ran at a 0.6 ms median across 150 measurements, against results in the tens to thousands of milliseconds.
  • Load is open-loop. Edits are issued on a fixed cadence regardless of pending acknowledgements, so a slow tool faces the same offered load as a fast one.

Two measurement bugs found and corrected

Both were caught before publication and both are worth recording, because each produced numbers that looked plausible.

Cold sync was measuring EBS, not the tools. A volume restored from a snapshot faults its blocks in lazily, so whichever tool ran first in a job paid a large one-time cost — 434 s on Chromium — and whichever ran second read from page cache and paid 125 s, regardless of which tool it was. The fix faults the corpus in once per host, then drops the page cache before every measurement. The cold-sync table above uses the corrected method; the earlier figures were discarded.

Mutagen's memory read as a confident zero. Mutagen re-execs its daemon with a bare basename, so a full-path process pattern matched nothing and every mutagen memory figure reported 0 MB — not missing data, but a plausible-looking zero. Patterns are now lists of alternatives, and the aggregator refuses to report a resource series in which no process was ever matched.

Method, in brief

Each job runs one cell on one pair of machines, executing both tools back to back in a randomized order. For each tool the sequence is: destroy all prior state on both hosts and verify it is gone; restore every editable file from a pristine copy so both tools sync identical bytes; cold sync to digest-verified convergence; wait for verified quiescence; measure an idle window; run the workload; then confirm the trees reconverged.

During the workload, N simulated agents rewrite files on a coding cadence from disjoint, precomputed working sets. One agent also measures: it announces the exact bytes it is about to write to a verifier on the receiving host, writes them, and waits for confirmation that precisely those bytes are readable at the destination path. Payloads are seeded from a per-run nonce, so content from an earlier run can never satisfy a verification.
