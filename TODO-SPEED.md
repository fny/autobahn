# Speed

Where the remaining time goes, and what would take it back. Every item names the measurement that would decide it, because the analysis estimate has been wrong every time it was tried; nothing here ships without an A/B (`bench/ab.sh`, now with `--remote HOST` for a destination over ssh, and `tc netem` on a loopback alias for a link with latency).

Numbers are from 2026-09-22 on an 8-core c6i-class box unless a cell name says otherwise. Base is 0.4.0 at `6b67b4a`.

## Done — concurrency, measured and committed

- [x] Both endpoints watched at once (`51f4325`). One editor: p90 125 → 52 ms, p99 140 → 55 ms local; p90 129 → 54, p99 149 → 60 over ssh. p50 unchanged. This was the 125 ms half-slice step in `Session::await_change`, the plateau the `5k-1` cell lost to mutagen on.
- [x] The scan walk spread over threads, one subtree each (`c4e4109`). 160k-file cold scan 7–34 s → 2.9 s. Warm walk unchanged. Capped at 8 threads per scan, cut to the host's cores.
- [x] A transition spread over threads (`f68b0a8`). 40k cold sync 5.6 → 4.5 s; 1,000-file burst cycle 165 → 120 ms (ten reps, no overlap).
- [x] The transition sent right behind the last push (`23e9145`). At 10 ms one-way delay: p50 123 → 104, one round trip of the ~3.5 an edit paid.
- [x] ~~Transfer pipeline depth 1 → 4~~ — measured, nothing: cold sync over ssh 7.7/6.6 → 7.1/7.1 s. Dropped. The pull side is not the bottleneck; apply was.
- [x] `COMPATIBILITY_EPOCH` 12 → 13 (`17715e9`, with the generation-carrying answers the scan skip needed). An agent that never scans measures its wait from the last change it reported; a same-versioned stale agent would have answered `true` forever on that channel.

## Round trips — the largest remaining win off a LAN

An edit cost ~2.5 round trips to a remote beta: the beta scan, `StageBegin`, and push + transition. Measured slope on base was 7 ms of p50 per ms of one-way delay; each round trip is 2 ms/ms.

- [x] A standing watch stands in for the beta scan (`17715e9`). Scan and transition answers carry the agent's generation, the watch waits from it and says whether the root is watched, and a cycle reuses the last snapshot while the watch stands. 1 editor at 10 ms one-way: p50 101.8 → 82.2, one round trip. A watcher in backoff answers "not watching" and is never skipped; a snapshot older than a minute is not reused, so the periodic full walk still runs. Epoch 13.
- [x] Small files go before the destination answers (`ad613e0`). Files are named in the transfer rather than positional, the receiver drops what it did not ask for, and when everything was sent the transition follows the content without waiting for the staging answer. 1 editor at 10 ms one-way: p50 56.0 → 34.8, one round trip; LAN within the spread. Files over 64 KB still wait for the answer, which may carry a delta signature or a "no".
- [x] An edit to a remote beta is now one round trip plus the work: at 0.4.0 it was ~3.5. On a 40 ms link, ~180 → ~60 ms.

## Cold sync — the second hash

- [x] ~~Skip the re-read in `publish_file` by verifying the staged inode's identity (device, inode, size, ctime) against what receipt recorded.~~ Built and measured 2026-09-23: the 1,000-file burst cycle 0.12–0.13 → 0.12–0.14 s, the 40k cold sync within the run-to-run spread. The re-read is page-cached and hashing is fast; the second hash is not a cost worth a change to the safety path. Dropped.
- [x] The rsync delta on the source (`supply_pull`) is one thread. Only matters for large files on a cold sync or a patch cell; measure `chromium-1-patch` before touching it. **Measured and fixed 2026-09-24 in `0a9966e` on the review box (c6i.8xlarge), a 1 MB change at a random offset in a 4 GB file, one-shot sync over ssh to localhost: 15.5 s. One core was busy for 11 s of it: the destination signing its base (2.7 s), the source computing the delta (the controller spent 4.1 s of CPU, 60% of it in the weak checksum), the destination rebuilding and hashing (2.7 s, already one streaming pass), then ~3 s of writeback. The weak checksum now reduces once instead of per byte (vectorizes), the delta checks the next base block by strong digest before any weak checksum, and bases of 64 MB or more are signed on up to eight threads: 15.5 → 11.5 → 8.8 s, controller CPU 4.1 → 1.5 s. What is left is the rebuild and the disk. The delta itself stays one thread: splitting it would mean buffering each range's literal data.**
- [x] ~~blake3 on a single large file is one thread.~~ Measured 2026-09-24 on a 2 GB file and closed. Warm in the page cache, blake3's multithreaded mode over a memory map hashes 4× faster (0.73–0.91 s → 0.18 s), but a memory-mapped file truncated mid-hash raises SIGBUS, and the scanner hashes files people are editing. Read into a 16 MB buffer and hashed across threads instead — safe — it is 10% faster warm (0.73 → 0.67 s; the copy costs as much as the hash) and slower cold from EBS (6.8–7.7 s → 7.7–7.9 s, disk-bound). Not worth a change.

## The warm walk — explained

Profiled 2026-09-23 (`perf`, `sync` on a converged 160k-file pair, 2.27 s wall, 1.9 s user, 3.4 s system). Not a runtime cost: a `watch` session on the same pair, after its 2.8 s cold start, ran 165 s without any cycle reaching the 1 s logging threshold — the periodic full walk of 160k files is under a second in a running session. The 2.2 s is the one-shot process's start:

- 30% `watch_tree` — registering inotify watches for the whole tree, one `statx` per entry, on both sides. A one-shot `sync` never waits, so it never needs them.
- 14% the scan itself (`probe_entry`, `scan_directory`), already parallel.
- ~10% thread wake-ups of the parallel walk (`futex`, `eventfd`, `schedule`): the helper budget spawns a thread per subtree.
- 2% deserializing the scan cache; reconcile 0.2%.

- [x] A one-shot `sync` no longer registers watchers (`verify` runs inside the supervisor, so it was never affected). Measured on the 160k pair, warm: 2.4–2.7 s → 0.7–0.9 s — more than the profile's 30%, since the registration walk was also most of the system time and the thread wake-ups.
- [x] ~~The parallel walk could pool its helpers rather than spawn per subtree.~~ Measured 2026-09-24 and closed: a cold scan of the 160k tree hands only 600–1,400 of its 16,161 directories to a helper (the rest are walked inline while every helper is busy), and a scoped spawn and join costs 65 µs here — 40–90 ms of CPU spread over the helpers, about 10 ms of a 0.5 s warm-cache scan, and nothing against a disk-cold one (53 s). A pool could save at most ~2%.

## Coalescing and the cycle's own overhead

- [x] `SETTLE`/`QUIET` 100/20 → 25/5 ms. The earlier reading — "an isolated edit does not wait it out" — was wrong: every change pays one QUIET, and with several editors the tree is never quiet. Measured 2026-09-23: one editor p50 47 → 25 ms; ten editors 48 → 22; a hundred 114 → 53. A 1,000-file burst converges in the same wall time (0.4 s) in two cycles instead of one; with no window at all it takes three and half again the cycle work, and a hundred editors go to 41 ms — a possible further step if throughput under bursts is measured and found fine.
- [x] `MAXIMUM_FOLLOW_UP_CYCLES = 5` stays. Measured at a hundred editors: 1 is slower (p50 +13 ms, p99 worse), 10 is within the spread. 
- [x] ~~The extra cycle after every transition.~~ Measured 2026-09-24 and closed. An isolated edit costs two cycles, local or over ssh — the edit's, and one woken by the session's own writes that finds nothing — and 24–29 ms of CPU in all. A cycle that finds nothing costs about 1.5 ms (a 40k-file session idles at 3.3 ms CPU/s with a heartbeat every 5 s, 3.0 with one a minute), so the extra one is ~5% of an edit's CPU, and it runs after the edit has landed, adding no latency. Suppressing wakes for a session's own writes would risk delaying a real edit to the same path; not worth it. The 3.0 ms/s left at idle is mostly the two-minute full walk — see MAC-BENCH.md §2.

## From the 2026-09-23 reviews

The six code reviews in `REVIEWS/` proposed these. They are estimates from reading the code, so the rule above applies: each names what would decide it. They are grouped by how clear-cut they look, not by expected gain.

### First — the likely largest latency win on large trees

- [x] **Remote snapshot processing is proportional to the tree.** Likely the largest latency left on large trees: the standing watch skips *idle* scans, but every edit changes the snapshot, so each one pays this in full. One changed leaf still serializes, hashes and signs both whole snapshots on the agent, and patches and decodes a whole one on the controller. The review measured, at 100 files per directory and one changed leaf: 10k files 5.2 ms agent / 1.2 ms controller, 100k 28 / 8 ms, 500k 132 / 43 ms, with a 40.6 MB snapshot producing a 38.7 KB delta. First measure how much of an edit's latency it is on a large tree — the `chromium-1` p50 from `bench-1790219288` against these per-scan costs — and how often a changed snapshot still crosses the wire in a `watch` session. Only then weigh structural deltas (a wire change) against caching the serialized baseline and its signature (idle memory). **Measured 2026-09-24 on a c6i.8xlarge, 420k-file Chromium tree, beta over ssh to localhost, 20 edits made on the beta: p50 633 ms, p90 640 ms. Of that, the agent spends 224 ms per changed scan (65 ms encoding and hashing the 45 MB snapshot, the rest diffing it against the baseline) and the controller 273 ms patching and decoding it — about 500 ms, ~78% of the edit. Edits on the local side do not pay it: with the standing watch, 245 of 247 remote scans in a local-edit window were skipped. So this is the cost of every edit made *on a remote machine* in a large tree, and the largest latency left. Caching the baseline encoding and signature on the agent would cut part of the agent share; the controller share needs a structural delta.** **Step one in `068c933` (branch `speed-review`): each side keeps the encoding its last delta produced, and the controller applies deltas against the block layout instead of a signature. Remote-side edits at 420k: p50 633 → 438 ms.** **Step two in `075dbbb`: a changed scan crosses the wire as its exact changes, applied copy-on-write and verified against the digest of the encoding they must produce (epoch 15). Remote-side edits at 420k: p50 438 → 266 ms — 633 → 266 in all.** **Step three in `48db241`: changed scans are verified with a Merkle-style tree digest cached per shared child list, instead of encoding and hashing the whole snapshot on each side; a cold digest of 420k files is 17 ms against 51 for encode-and-hash, and the agent warms it after each send. With mimalloc, codegen-units=1 and the reconcile memo in between, remote-side edits at 420k: p50 113 → 19 ms, first edit after start 85 ms, no fallbacks — 633 → 19 in all.**

### Small and clear-cut — build, then one before/after

- [x] **The change record fills with noise.** `PendingChanges::record` keeps duplicate paths, events from ignored subtrees on macOS, and the transition's own temporaries (`src/endpoint/local.rs:302-331`). A build in an ignored `target/` can fill the 8,192 cap and force a full walk every cycle. Dedupe, filter through the ignore set, drop `.autobahn-tmp` names. On Linux the watcher already skips ignored directories when it registers, so the pain is mostly FSEvents on macOS — see `MAC-BENCH.md`. Measure: full walks per minute during `cargo build` inside an ignored directory of a synced tree, on the Mac. **Measured on Linux 2026-09-24: a watch session on the 160k pair while one file took 50,000 separate appends in 1.2 s — no full walk (every cycle after startup 0.1–0.2 s), because the kernel merges consecutive identical inotify events, and ignored directories are never watched here. Our own temporaries add a handful of paths per transition against a cap of 8,192. On Linux there is nothing to fix; the ignored-`target/` case is FSEvents only and is MAC-BENCH.md §7.** **Built 2026-09-24 in `290ad1e` without a Mac measurement, because the fix is cheap and cannot lose a change: a path is recorded once however often it is reported, and on macOS nothing strictly beneath a directory the scanner prunes is recorded (it decides regions as the scanner does; the pruned directory itself is kept). Type-checked for aarch64-apple-darwin, logic tested on Linux. Confirming the full walks go away is MAC-BENCH.md §7. Found on the way and fixed in `cab6efa`: the Linux watch pruned ignored directories that a negation reaches into, so an edit to a re-included file went unseen until the 120 s walk.**
- [x] **Cross-filesystem staging tries the rename first** (`src/endpoint/local.rs:2221-2240`). On `EXDEV` it rehashes and copies. Compare `st_dev` once and go straight to the copy. More common than it sounds: any root on an external drive with its state in `~` pays a failed rename, a rehash and a copy per file. Measure: a cold sync with staging on another volume. **Measured and fixed in `014019e`: 1.2 GB cold sync into a tmpfs root with staging on disk, 5.52 → 5.10 s.**
- [x] **One-shot for configured and remote syncs.** The watcher skip that took a warm one-shot `sync` from 2.4–2.7 s to 0.7–0.9 s reaches only `sync ALPHA BETA` (`src/main.rs:923`). A configured `autobahn sync` builds its local endpoints with `one_shot: false` (`src/supervisor/mod.rs:1580`), and every agent does too (`src/transport/mod.rs:948`), so the remote side still registers a watch on every entry. Pass the intent through, and carry it to agents in `Initialize` — a wire change, so it waits for the next epoch bump, together with the free-space field in `FUTURE-FEATURES.md` rather than bumping twice. Measure: a configured `sync` on the converged 160k pair, local and to a remote beta, before and after. **Done in `1ad99e0`, on this branch's epoch 15: configured sync of the 160k pair, local 1.97 → 0.70 s, over ssh 2.8 → 1.4 s.**
- [x] **The transport scratch buffer frees its own case.** For 16 MiB chunks the compressed maximum is over the retention limit, so the buffer is dropped and re-zeroed on every chunk; it also keeps ~17 MB per thread otherwise (`src/transport/mod.rs:1043-1137`). Fix the threshold. Measure: RSS and CPU of a cold sync of large files, and RSS at 30 idle sessions. **Measured 2026-09-24 and closed. Supply batches aim for 8 MiB, so the per-chunk drop hits only messages over 16 MiB, now rare (changed scans go as changes, deltas in 4 MiB batches). Ten 200 MB cold syncs to one host over ssh, then idle: with the retention limit cut from 16 to 1 MiB the controller held 638 MB against 692 and the agent 9 against 23, and the sync took 15.7 s against 14.2 — re-zeroing costs more than the memory saves. The memory is the allocator, not the scratch: see the new idle-memory item.**
- [x] **`apply` removes changes one `Vec::remove` at a time** (`src/tree/apply.rs:61`) — O(k·n) on a flat directory, in folds and in journal replay. One merge pass per parent. Measure: emptying a flat 100k-entry directory, and replaying a journal that did. **Measured 2026-09-24 — worth fixing: emptying a flat directory through `apply` takes 0.10 s at 10k entries, 1.7 s at 30k, 24 s at 100k (quadratic, as claimed), and the same code runs in every fold and in journal replay.** **Fixed in `f133728` (branch `speed-review`): a directory's run of changes is one merge; 100k removals in milliseconds.**
- [x] **`digest_paths` walks the whole snapshot on every supply failure** (`src/endpoint/local.rs:898`). A burst of failures is quadratic. Build the digest → paths map once, on the first failure. Measure: a staged cycle with 10k failed supplies on a 500k tree. **Measured 2026-09-24 — worth fixing: one walk of a 500k-entry snapshot is 48 ms, so 10,000 failed supplies in a cycle cost about 8 minutes; building the digest map once on the first failure removes it.** **Fixed in `788150d`: indexed once per supply stream, on the first failure.**
- [x] **Smaller things.** `strip = true` in `[profile.release]` — the 6.9 MB binary is unstripped and is uploaded to every host, and with agents named by content every build is a new upload; measure size and first-contact time. `codegen-units = 1` separately: it slows every release build for maybe a few percent, so it needs a measurement of its own, not a ride on `strip`. `read_directory` sorts twice. ### Plausible — measure before touching

- [x] **Encoding and LZ4 run under the shared writer lock** (`src/transport/mux.rs:390-396`), so one 8 MiB `StagePush` blocks every other session to that host. Fan-out measured not superlinear; measure specifically a large-file push to a host while other sessions to it carry small edits. **Measured and fixed in `85db1db`: small edits while another session pushes 3 GB to the same host, p90 118/184 → 49/89 ms, max 222/274 → 62/111; p50 and quiet-time edits unchanged.**
- [x] **The observer builds its watcher while holding its state lock** (`src/endpoint/observer.rs:263-277`), so every session on that root waits out the initial walk, and again on each 30 s retry after watch loss. Sharing a root is cheaper than not, so whatever the lock serializes costs less than the second walk it saves. Closed without building.**
- [x] **Idle waits poll.** 25 ms slices in backoff and pause, a 50 ms accept poll on control, 250 ms on attach. The idle measurement above was one healthy session; the review's estimate is over 1,000 wake-ups a second with 30 failing or paused sessions. Measure that case before replacing polls with a condition variable per worker. **Measured 2026-09-24 — worth fixing, and it is the laptop case: 30 sessions to an unreachable host wake the supervisor 1,304 times a second and use 35 ms CPU/s (3.5% of a core), against 226 wake-ups and 10 ms CPU/s for 30 healthy idle sessions. A host asleep is the common way to be unreachable. (Paused sessions not measured: there is no `pause` command in this build to put them there.)** **Fixed in `e21b5ea`: a doorbell per worker rung by the control socket, the stop request checked every 250 ms, and poll(2) on the control socket. 30 unreachable sessions: 1,305 → 142 wake-ups/s, 30 → 6 ms CPU/s; 30 healthy idle: 226 → 138, 9 → 6.**
- [x] **The transition fold re-reads what it just wrote.** `fold_transition` keeps the lease's `scanned_at`, and published files have fresh mtimes, so the racy-mtime rule re-reads them on the next scan. The publish re-read above was closed as not worth it; this is a different read. Measure a cold sync larger than RAM, where the second read is from disk. (`docs/how-it-works.md` Decision 4 claims the rehash is saved; that claim is fixed in HYG-3 regardless.) **Measured 2026-09-24 — real: after a cold sync of the 40k tree (227 MB), the next sync read 135 MB where every later one read 11 MB (0.99 s against 0.78 s, all from page cache here). On a tree larger than RAM that is a second full read from disk of what the sync just wrote. The fix has to trust a digest the racy-timestamp rule refuses today — a write landing in the same mtime granule as the publish is the case that rule exists for — so it wants the publish to record the file identity it created (inode, ctime), not a looser rule. Worth doing for large first syncs; not urgent.** **Closed 2026-09-24 without building. The cost is one extra read of what a first sync wrote, and it only reaches the disk for a tree larger than RAM; avoiding it means trusting a digest the racy-timestamp rule refuses, and that rule is what catches a same-size rewrite landing in the same mtime granule as the publish. A missed edit is not a price for a one-time read. Revisit only with a design that records the published inode and ctime at nanosecond resolution and falls back on coarse filesystems.**
