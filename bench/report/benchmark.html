Two synchronization tools were given the same trees on the same hardware and asked to do the same work: carry a stream of file edits from one machine to another while simulated coding agents churned the tree underneath them. The question was not who transfers a tree fastest — that turns out to be a storage question — but how quickly a single edit becomes visible on the far side, and what each tool costs to keep running while it waits.

The short answer is that the two tools differ most where it is least visible in a feature list. On a 4,000-file tree they are comparable and mutagen is often quicker. On a real Chromium checkout, autobahn propagates a typical edit in about a quarter of a second where mutagen takes about seven, and it does so while holding roughly a seventh of the memory.

Steady-state propagation latency

This is the headline measurement: the time from a file being written on one machine to exactly those bytes being readable on the other, verified by digest. The clock starts and stops on the writing host, so no cross-machine clock error can enter, and the interval includes the verifying read and the acknowledgement's return trip. Every number here is therefore an upper bound on the tool's own propagation time.

The pattern that runs through every row is that autobahn's latency is close to flat in both tree size and agent count, and mutagen's is not. On the 4k corpus mutagen goes from 62 ms at one agent to 2,680 ms at a hundred; autobahn goes from 101 ms to 84 ms. Mutagen's cost tracks how much work it must redo to notice a change, which grows with both the size of the tree and the rate of churn in it. Autobahn's tracks the change itself.

This also explains the one result that looks anomalous. On a small tree with a single writer, mutagen can watch every directory natively and detect a change almost immediately — hence 62 ms, genuinely faster than autobahn's 101 ms. That advantage does not survive scale in either dimension.

The cell mutagen wins

Because 4k-1 was the single cell where mutagen led, it was re-run twenty times across fifteen distinct machine pairs — roughly 3,500 samples per tool — to establish whether the result was real. It is, and it is worth stating plainly.

Mutagen's slowest was just under five seconds.

Which tool is preferable here depends on what the latency is for. For a typical edit, mutagen arrives sooner. For the promise that every edit arrives quickly, autobahn is the stronger guarantee — roughly one mutagen edit in a hundred takes more than 2.7 seconds to appear.

The per-run medians are worth noting on their own. Across twenty runs on fifteen different machines, autobahn's median landed between 100.1 and 102.7 ms and mutagen's between 55.1 and 63.5 ms. Under 1.5% variation machine to machine means the harness is measuring the tools, not the hardware.

On the Chromium tree mutagen peaks at roughly 2 GB on the source host where autobahn uses 273 MB. The ratio is 2.6× on a 4,000-file tree and reaches 7.6× at 500,000 files, which is the signature of a per-file memory cost in the entry model rather than a fixed overhead. Two gigabytes is enough to matter on a laptop or a small VM; 273 MB is not.

The CPU column carries a quieter result. On the destination host, mutagen sustains more than a full core (104–124%) through the workload on Chromium, against roughly a third of a core for autobahn. The destination is doing no editing in these unidirectional cells — that cost is the price of noticing what changed.

First sync is a storage question

Cold-sync time was measured with the corpus faulted fully into the volume and the page cache dropped immediately before each run, so both tools read the tree from disk under identical conditions.

This is the expected result once storage is controlled for: transferring half a million small files is bound by device IOPS, not by either tool's logic. Roughly 505,000 files against a gp3 volume's baseline is most of the seven minutes on its own.

The practical reading is that first sync is not where these tools differ. The difference appears afterward, in how cheaply each one stays caught up.

Where autobahn loses

Two cells go against it, and both are worth stating.

  • Small tree, single writer. Mutagen's median is 1.6× better on 4k-1, confirmed over twenty repeats.
  • Extreme bidirectional load. At chromium-100-bidir — 200 agents editing 500,000 files in both directions at once — autobahn keeps the better median (6.1 s vs 10.0 s) but its 90th percentile degrades to about 19 s against mutagen's 14 s. Its tail discipline, which holds everywhere else, breaks down under that load. This cell also recorded the benchmark's only skipped ticks, meaning the offered edit rate was slightly reduced there for both tools.

Mutagen is also modestly faster to complete a first sync on every corpus measured, though by margins that sit inside the storage noise described above.

What makes these numbers trustworthy

The measurement plane is a single compiled binary deployed to both hosts, so both sides run byte-identical instruments and the rules for what counts as a file exist in exactly one place. The design was reviewed adversarially across five rounds, and every finding was fixed before any number here was collected.

  • Convergence is content-verified. A sync completes when the destination's digests match the source's, never when a file count matches — and only a tree walk that recorded zero errors can certify it.
  • The working set is fixed across agent counts. The measuring agent edits the same 40 files whether 1 or 100 agents are running, so concurrency changes load and nothing else.
  • Both tools run on the same pair, in an order randomized per job, so machine identity and ordering effects cancel instead of confounding.
  • Timeouts are censored data, not discards. An edit exceeding its deadline holds its position in the percentiles. Across all 57 jobs, zero samples were censored.
  • The harness measures its own overhead. The floor — arm, write, verify, acknowledge — ran at a 0.7 ms median, against results measured in hundreds of milliseconds.
  • Load is open-loop. Edits are issued on a fixed cadence regardless of pending acknowledgements, so a slow tool faces the same offered load as a fast one.

Two measurement bugs found and corrected

Both were caught before publication and both are worth recording, because each produced numbers that looked plausible.

Cold sync was measuring EBS, not the tools. A volume restored from a snapshot faults its blocks in lazily, so whichever tool ran first in a job paid a large one-time cost — 434 s on Chromium — and whichever ran second read from page cache and paid 125 s, regardless of which tool it was. The fix faults the corpus in once per host, then drops the page cache before every measurement. The cold-sync table above uses the corrected method; the earlier figures were discarded.

Mutagen's memory read as a confident zero. Mutagen re-execs its daemon with a bare basename, so a full-path process pattern matched nothing and every mutagen memory figure reported 0 MB — not missing data, but a plausible-looking zero. Patterns are now lists of alternatives, and the aggregator refuses to report a resource series in which no process was ever matched.

Method, in brief

Each job runs one cell on one pair of machines, executing both tools back to back in a randomized order. For each tool the sequence is: destroy all prior state on both hosts and verify it is gone; restore every editable file from a pristine copy so both tools sync identical bytes; cold sync to digest-verified convergence; wait for verified quiescence; measure an idle window; run the workload; then confirm the trees reconverged.

During the workload, N simulated agents rewrite files on a coding cadence from disjoint, precomputed working sets. One agent also measures: it announces the exact bytes it is about to write to a verifier on the receiving host, writes them, and waits for confirmation that precisely those bytes are readable at the destination path. Payloads are seeded from a per-run nonce, so content from an earlier run can never satisfy a verification.
